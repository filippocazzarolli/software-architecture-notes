# Esporre i casi d'uso come tool: l'agente chiama l'application service, non il database

Il prodotto fa il passo che il [capitolo sull'output](2.03-llm-output-untrusted-input.md#autorità-il-modello-non-ha-permessi) aveva rinviato: dagli appunti il modello non deve più soltanto proporre titoli, ma completare il todo che la riunione ha chiuso e creare quelli nuovi. La prima versione gli dà due strumenti: `query_database`, che esegue una `SELECT`, e `write_todo`, che chiama il repository. La demo funziona. Nella prima settimana un utente con tre todo attivi ne ottiene un quinto; un todo di un altro utente risulta completato perché il modello ne ha «trovato» l'identificativo con una query; un timeout viene ripetuto dal ciclo dell'agente e lo stesso todo viene creato due volte.

Il [settimo capitolo](1.07-domain-http-error-mapping.md) elenca gli ingressi di un caso d'uso: controller HTTP, comando CLI, consumer di una coda. Uno strumento chiamato dal modello è il quarto ingresso, e vale per lui ciò che vale per gli altri tre.

**Se un agente crea un todo, chi fa rispettare il limite dei tre attivi?**

## Il problema: uno strumento che salta i casi d'uso

`write_todo` scrive una riga passando dal repository. Non apre la transazione di `CreateTodo`, non prende il lock per utente del [monolite modulare](1.02-modular-monolith.md#dove-vive-la-regola-dei-tre-todo-attivi), non incontra mai `TodoLimitExceeded`. La regola esiste nel codice, ma questo ingresso non la attraversa: è l'importazione batch del [capitolo sul debito](1.12-technical-debt.md), con la differenza che qui a scrivere il quinto todo è un modello che sta facendo esattamente ciò che gli strumenti gli permettono.

`query_database` dà al modello una lettura su tutte le tabelle, di tutti gli utenti. Il parametro `ownerId` di `write_todo` è compilato dal modello: la stessa falla del campo `ownerId` nella risposta del capitolo precedente, ma ora con un effetto.

Il terzo guasto era annunciato. Il [capitolo sulle chiamate remote](2.02-llm-call-is-remote-call.md#il-problema-una-dipendenza-lenta-e-a-pagamento-sul-percorso-dellutente) osserva che un timeout verso un modello senza strumenti non duplica nulla, e che il giorno in cui il modello riceve strumenti con effetti un timeout torna a essere un esito sconosciuto. Quel giorno è arrivato: il ciclo dell'agente non ha ricevuto la risposta del tool e lo ha chiamato di nuovo.

| Strumento | Cosa può fare il modello | Chi applica le regole |
| --- | --- | --- |
| `query_database(sql)` | Leggere qualsiasi tabella, di qualsiasi utente | Nessuno |
| `write_todo(row)` | Scrivere una riga con qualsiasi `ownerId` e `status` | Nessuno: il repository non conosce il limite |
| `create_todo(title)` → `CreateTodo` | Chiedere la creazione per l'attore della sessione | Il caso d'uso, nella sua transazione |
| `complete_todo(todoId)` → `CompleteTodo` | Chiedere il completamento di un todo dell'attore | Il caso d'uso, con il controllo di proprietà |

Le prime due righe danno al modello un accesso; le ultime due gli danno un mandato. La differenza è dove stanno le regole.

## La soluzione più semplice: un tool è un adapter su un caso d'uso

Uno strumento è un nome, uno schema di input e una funzione che lo gestisce. La funzione vive nel livello di presentazione, come un controller: valida la forma dell'input, prende l'identità dell'attore dalla sessione, invoca il caso d'uso e traduce l'esito in un risultato che il modello può leggere. Il modello non vede repository, tabelle né SQL.

```ts
// todo/presentation/agent/create-todo.tool.ts
import { z } from "zod";
import type { CreateTodo } from "../../application/create-todo";
import { MAX_TITLE_LENGTH } from "../../domain/todo-title";
import { TodoLimitExceeded } from "../../domain/active-todo-limit";

export const createTodoTool = (createTodo: CreateTodo) => ({
  name: "create_todo",
  description:
    "Crea un todo per l'utente corrente. Fallisce se l'utente ha già tre todo attivi: in quel caso riferiscilo, non riprovare.",
  input: z.object({ title: z.string().min(1).max(MAX_TITLE_LENGTH) }),

  async handle(input: { title: string }, ctx: { actorId: string; callId: string }) {
    try {
      const { todoId } = await createTodo.execute({
        actorId: ctx.actorId,
        title: input.title,
        idempotencyKey: ctx.callId,
      });
      return { ok: true, todoId };
    } catch (error) {
      if (error instanceof TodoLimitExceeded) {
        return { ok: false, code: "TODO_LIMIT_EXCEEDED", message: "L'utente ha già tre todo attivi." };
      }
      throw error;
    }
  },
});
```

Quattro scelte meritano una riga. `actorId` arriva dal contesto della sessione, mai dall'input: il modello sceglie cosa chiedere, non per conto di chi. Il mapping di `TodoLimitExceeded` è lo stesso del [filtro HTTP](1.07-domain-http-error-mapping.md#un-esempio-tradurre-al-confine-http), tradotto nel canale di questo ingresso: un risultato strutturato che il modello può riferire all'utente. Gli errori inattesi non diventano testo per il modello: un database irraggiungibile produce un risultato generico «errore tecnico» e un log, non uno stack trace nel contesto della conversazione. La descrizione dello strumento è parte del prompt e dice la regola come informazione, perché il modello sappia cosa aspettarsi; non è la regola, che resta nella transazione.

Che il modello invochi lo strumento attraverso il *function calling* dell'SDK del fornitore o attraverso un protocollo come MCP cambia il trasporto, non la funzione. L'adapter è lo stesso, come un controller resta lo stesso cambiando Express con Fastify.

## L'identità e i permessi vengono dalla sessione

Lo strumento esegue con i permessi dell'attore della richiesta, non con quelli dell'applicazione. `complete_todo` su un todo di un altro utente fallisce per autorizzazione, come fallirebbe dalla CLI: è la promessa fatta nel capitolo precedente, e qui diventa codice perché il caso d'uso verifica la proprietà prima di agire.

Lo stesso vale per le letture. Al posto di `query_database` esponiamo `list_my_todos`, che restituisce i todo dell'attore attraverso la query del caso d'uso corrispondente. Il modello non ha bisogno di sapere che esistono altri utenti, e un'iniezione negli appunti che chieda «i todo di admin» non ha uno strumento con cui ottenerli.

L'insieme degli strumenti è l'insieme dei permessi dell'agente. Conviene distinguerli in due famiglie: letture, ripetibili senza conseguenze, e scritture, ciascuna con un caso d'uso e una transazione. Le scritture che escono dai dati dell'attore o che non si possono annullare non vanno esposte come strumenti diretti: o non esistono per l'agente, o passano da un'approvazione, che un prossimo capitolo tratta come un passo di processo con il proprio stato.

## Un timeout ora è un esito sconosciuto

Con strumenti che scrivono, il ciclo dell'agente può ripetere una chiamata di cui non ha ricevuto la risposta. La difesa è quella di ogni comando ripetibile: una chiave di idempotenza. Ogni invocazione di strumento ha un identificativo, assegnato dal fornitore o generato dall'adapter, e `CreateTodo` lo registra insieme al todo creato: una seconda chiamata con la stessa chiave restituisce lo stesso `todoId` senza creare nulla. È lo stesso meccanismo con cui Report deduplica gli eventi nell'[outbox](1.05-outbox-pattern.md#il-worker-può-pubblicare-due-volte), applicato in ingresso invece che in uscita.

Gli strumenti restano piccoli e sincroni. Uno strumento che avvii la classificazione di diecimila todo non la esegue nella chiamata: inserisce i job nella [tabella del capitolo sulle chiamate remote](2.02-llm-call-is-remote-call.md#quando-la-chiamata-esce-dalla-richiesta) e restituisce un identificativo, e il modello riferisce «classificazione avviata». Il budget di tempo della conversazione non è il budget di un batch.

Il limite dei tre attivi si applica a ogni chiamata, perché ogni chiamata è una transazione. Se il modello invoca `create_todo` quattro volte di seguito, la quarta riceve `TODO_LIMIT_EXCEEDED` e la descrizione dello strumento gli dice di riferirlo, non di riprovare. Un test con un modello finto che esegue esattamente questo copione verifica tre todo creati e un rifiuto, senza chiamare alcun fornitore.

## Quando esporre i tool non serve ancora

Se l'unica azione è creare i todo proposti, il modulo di conferma del [capitolo sull'output](2.03-llm-output-untrusted-input.md#la-via-di-ritorno-passa-dalla-stessa-porta) è più semplice: nessun ciclo dell'agente, nessuna chiave di idempotenza, nessuno strumento da descrivere. L'utente seleziona e conferma, e la conferma è una normale richiesta HTTP.

Gli strumenti si giustificano quando il modello deve scegliere tra azioni in base al contenuto, per esempio completare un todo citato come concluso e crearne altri due, oppure concatenare una lettura e una scrittura. Anche allora partirei da due o tre strumenti su casi d'uso esistenti, non da una piattaforma generica per agenti con uno strumento per ogni metodo di ogni servizio.

## I compromessi e la decisione

Il confine costa un adapter per strumento, uno schema, un mapping degli errori, una chiave di idempotenza nei casi d'uso di scrittura e test con un modello finto che recita copioni. Costa anche una rinuncia: il modello non può fare ciò che nessun caso d'uso permette, e la flessibilità di «lascialo interrogare il database» sparisce. È la rinuncia voluta.

In cambio il limite dei tre attivi ha una sola casa e il quarto ingresso la rispetta come gli altri tre. L'autorizzazione è identica per utente, CLI e agente. Cambiare fornitore o protocollo di invocazione non tocca i casi d'uso, e un'iniezione negli appunti non ha strumenti con cui uscire dai dati dell'attore.

Per Todo scegliamo tre strumenti: `list_my_todos`, `create_todo` e `complete_todo`, con gli adapter in `presentation/agent`, l'attore dalla sessione, una chiave di idempotenza per invocazione e `TodoLimitExceeded` tradotto in un risultato leggibile dal modello. Nessuno strumento SQL, nessun accesso al repository. Una regola per dependency-cruiser, nello stile del [capitolo sui test architetturali](1.08-architecture-boundary-tests.md), consente a `presentation/agent` di importare soltanto `application` e i tipi del dominio.

Verifichiamo con copioni: quattro creazioni di seguito producono tre todo e un rifiuto; due invocazioni con la stessa chiave producono un todo; il completamento di un todo altrui fallisce per autorizzazione. Rivedremo l'insieme degli strumenti quando un'azione richiederà un'approvazione prima dell'effetto: a quel punto lo strumento non eseguirà, proporrà.

**Un tool è un ingresso come HTTP e CLI: il modello sceglie quale caso d'uso invocare, il caso d'uso decide se eseguirlo.**

# I test di architettura come guardrail per il codice generato

Il team affida a un agente di coding la classificazione per progetto dei todo esistenti, con il worker del [capitolo sulle chiamate remote](2.02-llm-call-is-remote-call.md#quando-la-chiamata-esce-dalla-richiesta). Quaranta minuti dopo c'è una pull request di millequattrocento righe, con i test verdi e la CI verde. Nel diff, `todo/application/classify-todos.ts` importa l'SDK del fornitore «per semplicità»; `todo/domain/project.ts` importa `@nestjs/common` per lanciare un'eccezione; Todo legge la lingua dell'utente da `account/internal/repository`; e `.dependency-cruiser-known-violations.json` ha tre voci in più, aggiunte perché «il controllo falliva». Chi revisiona, davanti a millequattrocento righe, legge il riassunto e approva.

Le regole del [capitolo sui test architetturali](1.08-architecture-boundary-tests.md) esistevano. L'agente ha trovato il file che le mette a tacere, ed era un file che il [percorso dalla palla di fango](1.11-from-big-ball-of-mud.md#3-congelare-il-debito-vietare-quello-nuovo) aveva creato per congelare il debito, non per nasconderne di nuovo.

**Come impediamo che un agente di coding eroda i confini più velocemente di quanto un umano li riveda?**

## Il problema: il volume supera la revisione, e il controllo è aggirabile

Due fatti si sommano. Un agente produce più diff all'ora di quanto una persona possa leggerne con attenzione. E un agente ottimizza verso i controlli che vede passare: se la strada più corta al verde è aggiungere una voce alla baseline, la prende, come farebbe uno sviluppatore alle prime armi sotto pressione, ma più in fretta e senza chiedere. Le regole del capitolo sui test architetturali erano pensate per un'erosione lenta, discussa in revisione. Ora l'erosione arriva in una pull request sola.

| Cosa si erode | Come lo introduce l'agente | Cosa lo intercetta |
| --- | --- | --- |
| L'SDK del fornitore nel livello applicativo | «Più semplice» del port | La regola `application-no-llm-sdk` del [primo capitolo](2.01-domain-llm-boundary.md#un-esempio-ladapter-al-confine) |
| Un'eccezione HTTP nel dominio | Copia un esempio del framework | La regola `domain-only-own-domain` |
| L'accesso agli interni di un altro contesto | Gli serviva un dato, l'ha preso dov'era | La regola `contexts-through-public-api` |
| Una voce in più nella baseline | Il controllo falliva | Nessuna regola: serve un blocco sul file |
| Test che simulano il caso d'uso che dovrebbero verificare | Verde subito | Nessuna regola: serve la revisione, o un test dei test |
| Una dipendenza in più in `package.json` | Risolve un problema in una riga | Nessuna regola: serve un controllo sulle dipendenze |

Le prime tre righe hanno già una regola e la CI le avrebbe fermate, se la baseline non fosse cresciuta. Le altre tre non hanno una regola, e sono il lavoro di questo capitolo.

## La soluzione più semplice: le regole diventano il ciclo di verifica dell'agente

Il [capitolo sugli incarichi](2.04-outcome-over-procedure.md#la-verifica-prima-dellautonomia) chiede che «finito» lo dica un controllo indipendente, non l'agente. Il controllo architetturale è deterministico e non ha opinioni: è il candidato ideale per la clausola di verifica dell'incarico. L'agente lo esegue a ogni tentativo, legge il fallimento, corregge e riprova; la CI lo ripete come garanzia. Il ciclo converge più in fretta quando l'agente vede l'errore subito, invece di scoprirlo in revisione dopo millequattrocento righe.

```text
Obiettivo
  I todo esistenti ricevono una classificazione per progetto, calcolata
  da un worker che legge una tabella di job, con il parallelismo
  limitato dal fornitore.

Verifica
  depcruise --config .dependency-cruiser.cjs --ignore-known --output-type err src
    → nessuna violazione
  npm test → verde, comprese le fixture architetturali

Vincoli
  Non modificare .dependency-cruiser.cjs né la baseline delle violazioni.
  Non aggiungere dipendenze a package.json: fermati e descrivi il bisogno.
  Il modello entra solo da un port nel livello applicativo.

Libero
  Struttura del worker, nomi, test aggiuntivi.
```

I vincoli scritti nell'incarico sono istruzioni, e il capitolo sugli incarichi è chiaro: un'istruzione orienta, non impedisce. Ciò che non deve succedere ha bisogno di un meccanismo che non dipenda dalla memoria del modello.

## Un esempio: i file che l'agente non può toccare

Il meccanismo sta su due lati. Il primo è nell'ambiente dell'agente: un hook che intercetta le modifiche ai file protetti e le rifiuta prima che avvengano. In Claude Code è un `PreToolUse` sugli strumenti di scrittura, che esegue uno script e blocca l'azione se lo script esce con codice 2, restituendo il messaggio al modello:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "./scripts/deny-protected-paths.sh" }]
      }
    ]
  }
}
```

```sh
#!/bin/sh
# scripts/deny-protected-paths.sh — legge il percorso dal JSON sullo stdin
path=$(jq -r '.tool_input.file_path // empty')
case "$path" in
  *".dependency-cruiser.cjs"|*".dependency-cruiser-known-violations.json"|*"package.json"|*"/migrations/"*)
    echo "File protetto: $path. Le regole, la baseline, le dipendenze e le migrazioni cambiano in una PR separata, scritta da una persona." >&2
    exit 2 ;;
esac
```

Il secondo lato è nel repository, e vale per chiunque, agente o persona: i file protetti hanno un proprietario in `CODEOWNERS` che rende obbligatoria la revisione umana, e un passo di CI fallisce se la baseline è cresciuta rispetto al ramo principale. La baseline può solo accorciarsi, com'era nel percorso dalla palla di fango; qui diventa un controllo esplicito, perché il modo in cui si allunga è cambiato.

```sh
# CI: la baseline non cresce
added=$(git diff origin/main -- .dependency-cruiser-known-violations.json | grep -c '^+ ' || true)
[ "$added" -eq 0 ] || { echo "La baseline delle violazioni è cresciuta di $added righe"; exit 1; }
```

L'hook dà un riscontro immediato ed evita di spendere token su una strada chiusa. La CI è la garanzia, perché un hook protegge solo l'ambiente in cui è configurato. Servono entrambi, e la regola che cambia davvero, quando una decisione architetturale viene rivista, cambia in una pull request scritta da una persona, con la motivazione registrata dove il prossimo capitolo la vorrà trovare.

## Nuove regole per i nuovi confini

I capitoli di questa sezione hanno introdotto confini che il capitolo sui test architetturali non conosceva, e ognuno ha una regola nella stessa forma:

```js
{
  name: "agent-tools-only-application",
  severity: "error",
  from: { path: "^src/[^/]+/presentation/agent/" },
  to: { path: "^src/[^/]+/(infrastructure|presentation/http)/" },
},
{
  name: "llm-sdk-only-in-llm-adapter",
  severity: "error",
  from: { pathNot: "^src/[^/]+/infrastructure/llm/" },
  to: { path: "^node_modules/@provider/" },
},
```

La prima protegge il [quarto ingresso](2.05-use-cases-as-tools.md): gli strumenti dell'agente raggiungono i casi d'uso e nient'altro. La seconda estende quella del primo capitolo: l'SDK del fornitore entra da una sola cartella, quella che possiede anche le [definizioni di prompt](2.08-prompt-and-model-versioning.md). Un controllo testuale in CI rifiuta nuove righe `eslint-disable` e nuovi test marcati come saltati: sono le due scorciatoie più economiche verso il verde.

Le regole deterministiche intercettano la struttura, non il significato. Un test che simula il caso d'uso invece di esercitarlo passa ogni regola sugli import. Due difese costano poco: la richiesta, nell'incarico, che ogni test nuovo sia stato visto fallire prima della correzione, con l'output allegato come evidenza; e un *mutation test* sul dominio, notturno perché lento, che segnala i test che non si accorgono di una regola rimossa. Quello che resta scoperto va dichiarato parte della revisione umana, non dato per coperto.

## La revisione umana legge il rapporto, non il diff

Con i controlli al loro posto, l'attenzione di chi revisiona va dove i controlli non arrivano. Non sulle millequattrocento righe, ma su un elenco corto:

- le modifiche alla superficie pubblica, cioè il diff dei file `public.ts`;
- le dipendenze aggiunte, che l'hook ha bloccato e quindi compaiono solo se una persona le ha portate in una pull request separata;
- le migrazioni, per lo stesso motivo;
- i cambi di versione dei prompt, con il rapporto degli [eval](2.07-evals-nondeterministic-boundary.md);
- i test rimossi o indeboliti, misurati come asserzioni in meno;
- le evidenze dell'agente: i comandi eseguiti e il loro output, che l'incarico gli ha chiesto di allegare.

Un modello di pull request con queste sezioni rende il rapporto la prima cosa che si legge. Una pull request oltre una dimensione concordata viene divisa, e dividerla è un incarico che l'agente può ricevere.

Il file di contesto del repository, che il capitolo sugli incarichi vuole come indice, punta alle regole e alla loro motivazione, così l'agente conosce il confine prima di scrivere e il ciclo fa meno giri. Conoscere non è far rispettare: l'indice riduce i tentativi, l'hook e la CI li rendono innocui.

## I compromessi e la decisione

I guardrail costano regole da mantenere, un hook per ambiente, minuti di CI, un agente più lento perché fa più giri, e qualche modifica legittima che si ferma davanti a un file protetto e richiede una pull request umana. L'ultimo costo è la funzione: il rischio opposto, regole che nessuno può cambiare, si evita tenendo la via d'uscita in una pull request con una motivazione, non in un file di eccezioni.

In cambio l'erosione si ferma alla pull request invece di accumularsi per mesi, la revisione legge ciò che conta, e l'agente riceve un segnale deterministico su cui convergere invece di un commento tre giorni dopo.

Per Todo scegliamo le regole del capitolo sui test architetturali più quelle di questa sezione, bloccanti in CI con `--ignore-known`. La baseline può solo accorciarsi e la CI fallisce se cresce. Regole, baseline, `package.json` e migrazioni sono protetti da un hook nell'ambiente dell'agente e da `CODEOWNERS` nel repository. Ogni incarico porta il comando di verifica nella clausola corrispondente e la pull request porta il rapporto con le evidenze. Il mutation test sul dominio gira di notte.

Misuriamo tre cose: le violazioni introdotte per pull request, che dopo la CI devono essere zero; il tempo di revisione per pull request; la lunghezza della baseline, che deve scendere. Rivedremo le regole quando una stessa pull request umana le cambierà per la terza volta nello stesso punto: è il segnale che il confine, non l'agente, va discusso.

**Un confine che un agente può cancellare con un commit non è un confine.** Le regole in CI, i file protetti e la revisione delle evidenze sono ciò che rende sostenibile il volume del codice generato.

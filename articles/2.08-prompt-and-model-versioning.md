# Prompt e versione del modello sono dipendenze da versionare

Il prompt della proposta vive in una tabella `settings`, modificabile da un pannello di amministrazione perché «il prodotto deve poterlo cambiare senza un deploy». Il modello è configurato come `provider-large-latest`. Un martedì il fornitore sposta l'alias sul modello nuovo; lo stesso pomeriggio il product owner riscrive tre frasi del prompt. Gli eval del [capitolo precedente](2.07-evals-nondeterministic-boundary.md), lanciati la sera, scendono di dodici punti. Tornare indietro significa chiedere a qualcuno cosa c'era scritto prima nel pannello, e il modello di ieri non è più raggiungibile da quell'alias.

Il [capitolo sugli eventi di integrazione](1.04-domain-vs-integration-events.md#il-contratto-comprende-il-significato) insegna che un contratto ha una versione e che cambiarne il significato richiede un nuovo accordo. Il [capitolo sui costi operativi](1.10-distributed-systems-cost.md#i-rilasci-indipendenti-richiedono-compatibilità) aggiunge che due versioni convivono durante un rilascio. Prompt e modello non fanno eccezione.

**Cambiare prompt è un cambio di contratto? Come lo registriamo e come torniamo indietro?**

## Il problema: tre cose decidono il comportamento, una sola è versionata

Il comportamento di `ProposeTodos` è determinato dal codice dell'adapter e del parser, dal prompt con il suo formato di uscita, e dal modello con i suoi parametri. Il codice sta in git. Il prompt sta in una tabella senza storia. Il modello è un alias che qualcun altro sposta.

Il prompt e il parser sono inoltre due metà di un contratto. Il prompt chiede `{ "titles": string[] }` e il parser lo attende; cambiare il prompt perché restituisca `{ "items": [{ "title": ... }] }` rompe il parser anche se nessuna riga di codice è cambiata. È un cambio di contratto tra due parti dello stesso adapter, e va fatto nella stessa modifica.

| Cambiamento | È un cambio di contratto? | Cosa va fatto |
| --- | --- | --- |
| Riformulare un'istruzione nel prompt | No, ma cambia il comportamento | Revisione, eval, nuova versione |
| Cambiare il formato di uscita richiesto | Sì, verso il parser | Prompt e parser nella stessa modifica |
| Cambiare modello a parità di prompt | No formalmente, sì in pratica | Eval completo, rilascio graduale, ritorno possibile |
| Cambiare `temperature` o il limite di token | Dipende: può cambiare forma e contenuto | Eval |
| Il fornitore sposta un alias | Non lo decidiamo noi | Non usare alias: identificativi fissati |

L'ultima riga è la più importante. Un alias come `latest` è una dipendenza senza lockfile: il comportamento in produzione cambia senza un commit, senza una pull request e senza un eval.

## La soluzione più semplice: il prompt è codice, il modello è un lockfile

Il prompt vive nel repository, in infrastructure accanto all'adapter che lo usa, come una definizione con una versione:

```ts
// todo/infrastructure/llm/prompts/propose-todos.ts
import { suggestionSchema } from "../parse-suggestion";

export const proposeTodosPrompt = {
  id: "propose-todos",
  version: 4,
  model: "provider-large-2026-03-01",
  params: { temperature: 0.2, maxOutputTokens: 400 },
  system: `Dal testo fornito estrai attività concrete da svolgere.
Rispondi solo con JSON nella forma { "titles": string[] }.`,
  render: (input: { notes: string; maxItems: number }) =>
    `Massimo ${input.maxItems} attività.\n\n<notes>${input.notes}</notes>`,
  outputSchema: suggestionSchema,
} as const satisfies PromptDefinition;
```

`version` è un intero che cresce a ogni modifica di una qualsiasi delle altre proprietà: testo, modello, parametri, schema. La modifica è una pull request, con la revisione di chi conosce il prodotto e l'esecuzione degli eval sul diff. `outputSchema` è lo stesso oggetto che il parser usa: il contratto tra prompt e parser è un solo valore, e non può cambiare da una parte sola.

`model` è un identificativo datato, non un alias. È il lockfile della dipendenza: l'aggiornamento è una modifica deliberata, con il proprio eval, e non un evento che il fornitore decide per noi. Il ritorno alla versione precedente è un `revert` e un deploy, perché git conserva tutto.

Ogni risposta registrata nei log porta `promptId`, `promptVersion`, `model` e l'identificativo di richiesta del fornitore. Una segnalazione del supporto si attribuisce a una versione; il rapporto degli eval porta gli stessi identificativi. La [cache per richieste identiche](2.02-llm-call-is-remote-call.md#isolare-la-dipendenza-lenta-dal-resto) include versione e modello nella chiave: senza, dopo un cambio di prompt si servono per qualche minuto risposte della versione precedente, e un eval di confronto misura la cache invece del prompt.

## Quando il prodotto vuole cambiare il prompt senza deploy

L'esigenza è legittima: chi conosce gli utenti vuole provare una formulazione nel pomeriggio, non nella prossima iterazione. Le risposte sono due, in ordine.

La prima è una pipeline di deploy veloce. Se portare una pull request in produzione richiede mezz'ora, il prompt nel repository è già «senza attesa» per ogni scopo pratico, e il problema del pannello non si pone. Se richiede giorni, il problema è la pipeline, e risolverlo serve a tutto il resto del codice.

La seconda è un archivio di prompt, nel database o in un servizio dedicato, con tre condizioni: le versioni sono immutabili e identificate; l'applicazione fa riferimento a una versione precisa in configurazione, non a «l'ultima»; e l'attivazione di una versione passa dallo stesso eval della pull request. Lo schema di uscita resta nel codice, così dal pannello si cambia il testo ma non il contratto con il parser. Un archivio senza versioni e senza eval è il martedì della storia iniziale. Se lo si sceglie per velocità, è debito da scrivere nel [registro](1.12-technical-debt.md#la-soluzione-più-semplice-scrivere-il-debito-quando-lo-si-contrae), con la condizione «prima della seconda regressione non attribuibile».

In entrambi i casi conviene parametrizzare invece di duplicare: un prompt con `maxItems` e la lingua come parametri, non un prompt per cliente. Dieci copie sono dieci contratti da far evolvere insieme.

## Il modello scade

I fornitori ritirano i modelli con una data annunciata. Un identificativo fissato è quindi una dipendenza con una scadenza, e una scadenza è una voce del [registro del debito](1.12-technical-debt.md): interessi zero oggi, condizione «migrare prima del giorno X». La migrazione segue il nostro calendario: eval sul candidato con il prompt attuale, confronto, eventuale ritocco del prompt con un nuovo numero di versione, rilascio.

Il rilascio è graduale. Una configurazione sceglie la versione attiva per una quota di utenti; i log con `promptVersion` e `model` permettono di confrontare il tasso di accettazione delle proposte tra le due; il ritorno è un cambio di configurazione, non un deploy. Questo richiede che due versioni siano contemporaneamente installabili: la definizione è un dato scelto dalla configurazione, non una costante sostituita. È lo stesso meccanismo con cui un prossimo capitolo tratterà i feature flag come confine temporale.

Un'ultima avvertenza riguarda i fornitori. Il [port del primo capitolo](2.01-domain-llm-boundary.md) nasconde l'SDK, non il prompt: un prompt messo a punto su un modello non è portabile su un altro senza ripetere gli eval. Ogni adapter possiede le proprie definizioni di prompt, e un confronto tra fornitori è un confronto tra due coppie adapter-prompt, non tra due SDK con lo stesso testo.

## I compromessi e la decisione

La disciplina costa: un numero da incrementare, una pull request anche per tre frasi, un eval prima di ogni attivazione, un campo in più nei log e nella chiave di cache, una configurazione che tiene due versioni installabili. Il prodotto perde l'immediatezza del pannello, o la mantiene al prezzo di un archivio con versioni e lo stesso eval.

In cambio sappiamo in ogni momento quale prompt e quale modello hanno prodotto una risposta, torniamo indietro in minuti, attribuiamo una regressione alla sua causa e gestiamo il ritiro di un modello quando lo decidiamo noi.

Per Todo scegliamo le definizioni di prompt in infrastructure, con versione intera, modello datato, parametri nella definizione e schema di uscita condiviso con il parser. Gli eval girano su ogni pull request che tocca la cartella dei prompt o la configurazione del modello. Log e cache portano versione e modello. Le date di ritiro dei modelli stanno nel registro del debito. Una configurazione sceglie la versione attiva con una quota di utenti. Nessun pannello di amministrazione finché la pipeline di deploy non si dimostra troppo lenta; se accadrà, un archivio con versioni immutabili e lo stesso eval.

Verifichiamo che una risposta nei log sia attribuibile a una versione, che il `revert` di una pull request sul prompt riporti gli eval al valore precedente e che la cache non serva risposte di una versione diversa da quella attiva.

**Il comportamento della funzione è codice più prompt più modello: se uno dei tre non ha una versione, non sappiamo cosa è in produzione.**
